# 2026-09-08 — Rediseño del alta en Alumnos.aspx: modelo Usuario / Alumno / Familia

## Contexto / pedido original

Se pidió revisar el estado de `Alumnos.aspx` (pantalla de gestión de alumnos) y rediseñar por completo la lógica de alta de un alumno. El diagnóstico inicial encontró:

- El alta generaba usuario (`cliente_{dni}`) y contraseña automáticamente, **sin mostrarla nunca** al admin (bug real).
- `MPPUsuario.DniExiste` bloqueaba a propósito que un DNI ya registrado (con cualquier rol) pudiera tener también un registro en `ALUMNOS` — impedía que, por ejemplo, un Entrenador se anotara también como Alumno.
- No existía manejo de menores de edad ni de tutores/familiares.

## Flujo acordado con el usuario

1. Admin completa DNI + fecha de nacimiento (y el resto del formulario) en `Alumnos.aspx`.
2. Al completar la fecha de nacimiento se calcula la edad automáticamente.
3. **Mayor de 18**: se busca el DNI en `USUARIOS` (cualquier rol).
   - No existe → popup para completar datos y crear Usuario + Alumno.
   - Ya existe (Cliente, Entrenador, etc.) → preguntar si se lo asocia también como Alumno.
4. **Menor de 18**: preguntar si se asocia con un familiar (madre/padre/tutor).
   - Sí → pedir DNI del familiar, aplicar el mismo flujo de búsqueda (punto 3) pero **para encontrar/crear al familiar, no como Alumno** — el familiar solo necesita existir como `Usuario` (rol Familiar si es nuevo). Una vez resuelto, el menor queda vinculado a la cuenta del familiar.
   - No → aplicar el flujo del punto 3 sobre el DNI del propio menor (autogestionado).
5. Modelo de datos: 3 tablas — `USUARIOS` (identidad), `ALUMNOS` (rol), y tabla intermedia nueva **`ALUMNOS_USUARIOS`** (N:N) — reemplaza la columna única `ALUMNOS.usr`. Permite: varios familiares por alumno, varios alumnos por familiar, y que un mismo DNI tenga cuenta con un rol (ej. Entrenador) y además figure en `ALUMNOS`.
6. Rol nuevo y dedicado: **Familiar** (no reutiliza el rol Cliente).
7. Contraseña: campo editable por el admin en el alta; si se deja vacía se autogenera **y se muestra una única vez** en un modal (antes se perdía sin mostrarse nunca).

Decisiones confirmadas explícitamente por el usuario (vía preguntas antes de implementar):
- Tabla intermedia `ALUMNOS_USUARIOS`, no reutilizar `usr`.
- Rol Familiar dedicado (terminó siendo el rol numérico `6`, porque el `5` ya estaba tomado en código por `RolWebMaster` aunque nunca pudo persistirse — se aprovechó la migración para habilitar también el `5`).
- Contraseña: editable por el admin con fallback a autogenerada.
